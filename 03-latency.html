Part 03 · Timing and evaluation

Measure delay, jitter, and reliability

A real-time pipeline is not defined only by how fast it seems to run. Measure how old the data are when your algorithm receives them, how long processing takes, and when the physical stimulus actually occurs.

Three timing quantities

Latency / delay

The time between an event and the corresponding response later in the system. Often reported as mean or median delay.

Jitter

Trial-to-trial or update-to-update variation in that delay. Report SD, percentiles, and worst observed values.

Throughput

How often new data arrive and how quickly your code can process them. A fast algorithm can still receive data in large, infrequent chunks.

Delay calculator: what does a fixed delay mean in phase?

For an oscillation with frequency f, a delay of t seconds corresponds to a phase lag of 360 × f × t degrees when the delayed signal is compared with the undelayed reference. This is an intuition aid; use the measured frequency and measured end-to-end delay in the real experiment.

Example: 10 Hz and 20 ms correspond to a 72° phase lag. A fixed delay can be compensated by applying a phase advance of the same magnitude; variable delay (jitter) cannot be removed by one fixed correction.

A practical validation sequence

Measure the stream update interval. Log the time when MATLAB notices each new block and the number of new samples. This gives the observed update cadence and block-size distribution.
Measure processing time. Use tic/toc around the computation, separately from plotting and file writing.
Use a known test signal. Feed a known periodic signal into a suitable MEGIN auxiliary input, record it, and verify when the algorithm would have triggered.
Measure the physical output. Record the TTL output and, for visual stimulation, a photodiode signal. A software timestamp is not a substitute for measuring when light actually appears.
Repeat many times. Report mean/median, SD, 5th–95th percentile, maximum, and any missed or duplicate triggers. Inspect histograms and time trends.

Photodiode and trigger loop for visual experiments

A robust visual timing test uses a small photodiode marker on the display. The stimulus computer changes the marker with the stimulus frame; the photodiode's electrical output is recorded by MEGIN as an auxiliary channel. A separate TTL marker can indicate the software's intended trigger time.

Interpretation: the difference between TTL and photodiode onset estimates display-related delay. The difference between algorithm decision and recorded TTL estimates output-path delay. The complete system should be validated using the actual display, cable, trigger hardware, and acquisition configuration.

MATLAB timing log pattern

% Illustrative timing instrumentation inside your loop
tLoopStart = tic;

% 1) read new samples
tRead = tic;
% dat = ft_read_data(...);
readSeconds = toc(tRead);

% 2) run your signal processing
tProc = tic;
% feature = calculate_feature(dat);
processingSeconds = toc(tProc);

% 3) store a record (do not write a file on every iteration)
logTime(end+1,1) = datetime('now');
logRead(end+1,1) = readSeconds;
logProcessing(end+1,1) = processingSeconds;
logLoop(end+1,1) = toc(tLoopStart);
Clock caution: datetime('now') is useful for a simple log, but it is not a precision synchronization solution across computers. For precise end-to-end timing, use a common recorded signal/trigger and appropriate clock synchronization, then verify with the acquisition data.

What to report

  • MEGIN model, DACQ version, bridge version, FieldTrip version, sampling rate.
  • Chunk size / update interval and whether bridge and client are on the same computer.
  • Processing time distribution and any dropped or late updates.
  • End-to-end delay distribution measured from recorded physical signals.
  • Display refresh rate, photodiode placement, and trigger hardware.
